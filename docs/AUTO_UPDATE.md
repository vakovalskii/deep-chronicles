# Автообновление настольного клиента — схема следующего этапа

Статус: **проектирование, не реализовано**. Сейчас сайт раздаёт ZIP Windows/macOS и `release.json` с commit, URL, размером и SHA-256. Это основа проверки версии, но игрок пока скачивает обновление вручную.

## Пользовательский сценарий

Один ярлык запускает лаунчер. Он проверяет обновление, показывает загрузку и запускает игру. Если сервер обновлений недоступен, можно запустить уже установленную совместимую версию. Во время боя игра не закрывается ради обновления: новую версию активируем при следующем запуске.

## Устройство

1. Отдельный маленький лаунчер для Windows/macOS. Он не заменяет работающий EXE и не хранит учётные данные игры.
2. Версии лежат в отдельных каталогах, например `versions/<commit>/`. Лаунчер запускает выбранный каталог, а не перезаписывает занятые исполняемые файлы. Предыдущая версия остаётся для отката.
3. Манифест обновления содержит канал, идентификатор версии, платформу/архитектуру, минимальную версию лаунчера, совместимость протокола, URL, размер и SHA-256 пакета. Нельзя сравнивать Git-хеши как возрастающие номера: нужен явный порядок выпуска.
4. Манифест подписывается Ed25519 после успешных проверок. Открытый ключ встроен в лаунчер; закрытый находится только в секретах выпуска. Проверяем подпись исходных байтов, HTTPS, размер и хеш архива. SHA-256 из неподписанного JSON сам по себе не подтверждает издателя.
5. Загрузка идёт в `.part`; прерывание не затрагивает текущую версию. Распаковка проверяет пути (без выхода из каталога, абсолютных путей и неожиданных ссылок). Переключение текущей версии выполняется атомарно после полной проверки.
6. Токены и настройки остаются в существующем Godot `user://`; персонажи и прогресс остаются на сервере. ZIP с новой версией не содержит пользовательские файлы.
7. После первого успешного старта сохраняется отметка исправной версии. При неудачном запуске предлагается предыдущая совместимая версия; откат клиента не откатывает серверную SQLite.

Подпись update-манифеста и подпись Windows/macOS-приложения — разные задачи. Сейчас Windows signing/Apple notarization не настроены; автоматическая загрузка не заменяет доверие ОС к исполняемому файлу.

## Включение в существующий конвейер

После `native:verify -- --release` конвейер упаковывает версию, подписывает манифест и загружает пакет. Манифест канала публикуется последним, когда файлы уже доступны. Новая версия доступна игрокам только после этой операции.

Проверки: чистая установка; обновление предыдущего выпуска; оборванная загрузка; неверная подпись/хеш; недостаток места; запущенная игра; недоступный сайт; откат; сохранность interface.cfg и sessions.json. Сценарии должны выполняться и на Windows, и на macOS. Сам лаунчер тоже должен иметь отдельный безопасный путь обновления.

Android/iOS требуют отдельного решения под выбранный канал распространения. Настольный механизм замены EXE к ним не применяется.
